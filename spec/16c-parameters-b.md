## 16.C.1 Scope and rules

S16 says it is the single complete list of parameters (S16 16.1), yet 35 names used in S8, S6, S10, S11 and S13 are defined in neither S0 nor S16. This file gives each of them one disposition: a parameter row, an alias row, or an entry under "Not parameters" (the 16.C.8 list). Disposition count: 35 names, 30 parameter rows, 3 alias rows, 2 not-parameter entries. [D]

| Rule | Decision |
| --- | --- |
| R16C-1 Names | Exactly S0 0.10.1 and the names as the using part wrote them. No name is renamed. Where two names denote one thing, one is canonical and the other is an **alias row**: it is not seeded, a write to it is refused as unknown (`AC-param-14`), and the part that uses it is amended at assembly (`ISS-16101`, `ISS-16102`, `ISS-16103`). [D] |
| R16C-2 Defaults | Every default is labeled `initial configurable default` or is a formula over other defaults. A formula that uses the FD§3.3 inputs is not a measurement. No default here is a statistic. Where a default is a safety limit the cell says why that value is safe. [D] |
| R16C-3 Meaning | Type, unit, default and validation were taken from the passage that reads the name (about 15 lines around each cited line). Where the passages of two parts disagree the row says which value stands and an issue records it. [D] |
| R16C-4 Constraints | Relations that a passage states or that follow from its own formula get an id `S16C-C1`..`S16C-C14` (16.C.9). They are evaluated like `C1`..`C20` of S16 16.3, against the configuration as it will be at `effective_from`, so two individually valid edits cannot combine into an invalid state. An `error` refuses the write; a `warning` is returned and logged. [A] |
| R16C-5 Direction | Change-policy codes are those of S16 16.2.2. In words: `T↓` lowering is tighten-immediately and raising is loosen-with-notice; `T↑` is the reverse; `N` has no tightening direction and always needs notice. Notice is `change.notice_days_default` (7) except for `admission.*` (`change.notice_days_price`, 14). A loosening or neutral change also needs a second distinct `operator` (S16 16.2.3). Directions are assigned by the rule of 16.2.2 (tightening lowers risk to members, credit integrity or the platform without taking anything from an object that already exists); an owner who disagrees changes the cell. [A] |

Columns: `name` · `type` · `unit` · `validation` (range, relations) · `initial default` · `owner role` · `change policy` · `prospective-only` (what is stamped, what a change never touches) · `calibration` (the Phase 0 or Phase 1 measurement that replaces the default, codes of S0 0.10.4) · `used in` (part and line). Public exposure is true for every row except `lease.max_job_share_ratio`, which is proposed hidden with the anti-abuse rows of S16 16.17.5 [A]. Every row is prospective-only (FD Principle 5; S0 0.10.3): the column says what that means for the row.

## 16.C.2 UI budgets and low-bandwidth behavior

Owner `operator` (area `ui`, S0 0.10.5). The budgets are read by the CI build check (`AC-i18n-27`) and by nothing at runtime; a deployed build is never recalled when a budget changes, and the CI check uses the value in force when the build is made [A]. Lowering a budget below the size of the current build makes the next build fail, which is the intent of a tightening. All byte budgets are compressed sizes. Test input values are not claims about any network; real values come from the `TEC` measurement (FD§8.3 G2) and reachability checks (10b 10.15.4). [D]

## 16.C.11 Hypotheses, verifications, assumptions

**Hypotheses [H]**: `verify.reviewer_recheck_rate` = 0.10 is enough to see reviewer disagreement; gold fails are rare enough that `verify.gold_adjudication_rate` = 1.0 is affordable; 34 percent is a share that keeps jobs fillable with a pilot pool of 30 to 50 members; the 400 kbit/s and 0.4 s test profile behind `ui.budget.first_interactive_s` is a harness input only; `ui.draft.ttl_s` = 3,600 is long enough for a paste-back.

**Verifications [V]** (what, by whom, where stored): the rounding rule for `lease.max_job_share_ratio` and whether the S6.24 forecast accounts for it (S9.* and S6.* owners, in those parts); the meaning of `(1 - phi)` in 06b 6.24.3 (owner of S6.*); the content of the constraint 08b 8.31 proposes (owner of S8.*); the purge time of the uploads of a cancelled draft (S10.*); the S15 name of the free-text field of an appeal (S15.*); every `TEC`, `OPS`, `P1M`, `SEC`, `CAL` and `FND` measurement in the calibration column, stored as a `CalibrationRecord`, in the pilot report or in a `PreRegistration`.

**Assumptions [A]** (with what could overturn each): directions of change by the rule of S16 16.2.2 (owner decision on any row); canonical choices for the three alias pairs (owner or C-001 at assembly); the divisor rule for the two granularities; CI reading the budgets at build time; `S16C-C3`, `C8`..`C13` as warnings; `lease.max_job_share_ratio` hidden from the public parameter list.

**What this part cannot promise** [D]: every default is a starting value until its measurement exists; nothing here shows that any default is safe for real members, legal anywhere, or enough for the pilot; two-person approval of loosenings is only as strong as the number of distinct admins (`ISS-168`); the line numbers in the last column are those of main at 115c0ec and drift as parts are edited.
