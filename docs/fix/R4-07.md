## Read-back

**What 5.29.8 says (read first, with 5.29.6).** `settle()` is called only by the `settler` worker (and by the cancel path when a job has no in-flight cells). It is one transaction. It returns `already_settled` for a terminal job, raises `STATE_CONFLICT` if the job is not in `settling` (mode complete) or `cancelling` (mode cancel), and returns `not_yet` while any cell of the job is not in a terminal state, so settlement waits until every cell is terminal. Then it locks the escrow, pays the levy, refunds the rest, checks that the held amount equals payouts plus levy plus refund and that the escrow balance is 0, and moves the job to `settled` or `settled_partial`. 5.29.6 (`accept_cell`) calls `g_accept`; on DEFER it only marks the cell deferred and returns, so a deferred cell stays in `submitted` (or `flagged_for_audit`), which is not terminal. That is why an unresolved deferral would stop `settle()` for ever.

**A deferred blocked cell reaches a terminal state, so settlement can run.** (1) A member job in `running` has a `submitted` cell that `G-accept` defers (05b:187). Its `acceptance_deferred_until` is the job's current overrun deadline (05b:187, 05a:711), the same instant at which the `overrun_timeout` guard of JT-15 becomes true (05b:90). (2) At that instant the `job_progress` worker (05b:675) raises JT-15. Both guards are true, and 05b:90 now says the reason is `funding_shortfall`, so the job goes to `settling` with that reason and not with `overrun_timeout`. (3) Table 5.22.1 (05b:110) says a cell blocked by the payout guard is `voided` under `funding_shortfall`; the fan-out (CT-16, `job_fanout_worker`) moves it to `voided`, which is terminal. Other cells drain, pay or are cancelled by the same table. (4) When every cell is terminal, `settler` runs `settle()` (5.29.8); the job ends `settled_partial` (JT-17), because a primary cell is not `accepted`. (5) If `overrun_timeout` was recorded first and a cell is blocked only afterwards, `G-accept` (05b:187) now returns VOID for it in a `settling` job, and the `overrun_timeout` row (05b:107) says it is `voided`, so that cell is terminal too. (6) If JT-12 resumes a job after a pause, `paused_total_s` grows and the recomputed deadline moves with it (05b:187, 05a:711), so neither guard fires early.
