For each closure reason of 0.9.2 and for settling and cancelling, what happens to a submitted, flagged or deferred cell so that settle() always runs:

- policy_stopped (settling): submitted voided at G-accept (R9); flagged voided; a cell deferred earlier is run again at the transition and ends voided. settle() finds every cell terminal after the lease drain or revoke.
- service_revoked (settling): drain continues to acceptance and is paid, a blocked cell is VOID with the reason, a flagged cell with no audit cell in leased, submitted or flagged_for_audit is VOID; void policy voids both.
- template_retired (settling): submitted and flagged cells voided.
- operator_killed (settling): submitted and flagged cells voided.
- overrun_timeout (settling): submitted continue and are paid; blocked VOID; flagged without audit cell VOID; earlier deferral re-run and ends accepted or VOID.
- cells_exhausted (settling): the same as overrun_timeout, only non-primary cells can be in play.
- verification_shortfall (settling): submitted continue and are paid; blocked VOID; flagged without a payable audit VOID (CT-07 pool_ok false case included).
- funding_shortfall (settling): payout-guard blocked cell VOID, any other blocked cause VOID, flagged without audit cell VOID, other cells continue and are paid. The guard fires only from a running job, so no cell is left deferred.
- expired (settling, Commons): submitted continue and mint; Commons switch off, no mint headroom, donor suspended or template paused VOID; flagged without audit cell VOID.
- cancelling (JT-18): the same as overrun_timeout; the queued audit cell is cancelled by the cancel, so the flagged cell is VOID as soon as no audit cell is in leased, submitted or flagged_for_audit.
- a job entering settling from assembling (JT-14 or JT-15 operator_killed): the same rule, because it holds in every settling job.
