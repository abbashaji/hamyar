# Audit A12: spec/15a-api-core.md and spec/15b-api-admin.md

Reviewer: cell C-053, independent of the authors (C-020, C-021). Method: both files read completely in chunks against S0 (`spec/00-conventions.md`, read completely) and `docs/decisions.md`; the FD and `docs/source/prompt.md` were not re-read (see Not verified). Line numbers refer to the files as read before this audit's edits and are approximate to a few lines.

## Checked

- Endpoint rows (15a 15.5 to 15.8; 15b 15.22 to 15.33): method, path under `/v1`, auth, idempotency marker, rate-limit class, success status and events are present for every row; request, response and errors sit in the schema blocks (15a) or columns (15b); pagination is in the 15a 15.11 table and the 15b `Page` column. Found correct apart from the findings below.
- Error model: 15a 15.9 catalogue equals the S0 0.11.3 code set; every `code` and every `details.reason` used in rows, guards and examples exists in the catalogue (checked one by one). 15b uses only S0 codes and new `details.reason` values, which 15b declares as vocabulary inside `details`.
- Authentication separation: member endpoints accept only `member` tokens and answer `AUTH_INVALID` `wrong_scheme` otherwise (15a 15.4); every admin endpoint is under `/v1/admin/*` with the `admin` scheme and WebAuthn on a separate origin; no admin endpoint accepts a member credential and none of the member operations in 15b (share cards) is admin-authenticated. Public endpoints are `none`, cookie-free.
- Step-up and two-person: every `2P` action in 15b is in the S0 list or in the extension list of 15.22.4; the approval flow re-runs guards at execution, requires a distinct second admin and binds the step-up to the stored payload.
- Provider credentials and chat content: no endpoint in either file accepts or returns a provider credential, cookie, chat link, screenshot or chat-page content; `open_url` is human-opened, `reported_*` fields are attestations, terms copies and URLs are stored text and never fetched (15b 15.23, 15.35).
- Arithmetic: all three 15a worked examples recomputed (p_ucr 1,150,000; escrow 276,000,000; pool 24,000,000 giving 24 cells; levy 12,000,000; eta 869,565; capacity 320 and committed 264; lease expiry 1,200 s; lot expiry 60 days from 2026-11-12 is 2027-01-11; quote expiry 1,800 s; confirm time inside the quote window; balance after 24,000,000). 15b chunk math: 785,408 bytes per chunk and 7 chunks for 5,242,880 bytes. Ids in examples match the 0.6.3 regex (length checked).
- Launch gates and kill switches: 15b launch switch rule, switch blockers, gate sign-off flow, kill-switch keys, release guards and their consistency with S0 0.9.6, 0.9.8 and 0.10.6 Table C; 15a creation of members, jobs, leases and submissions against the gate matrix added by this audit.
- Idempotency: replay, mismatch and in-progress behaviour in 15a 15.4 and 15.10 agree with S0 0.11.5; natural idempotency exists for lease, submission, escrow hold and member creation.
- Pagination: cursor-only everywhere; 15b admin lists use `cursor`; orders are stated.
- Event model (15b 15.34): every S0 0.9 event name appears with payload, producer and consumers (job 19, cell 17, lease 5, submission 8, member, template 9, service 9, appeal 8, audit 8, escrow, reservation, report, gate, kill switch, ledger, parameter, policy, launch events compared name by name); events are written in the same transaction as the state change; rejections emit nothing.
- Ground rules: no automation of volunteer accounts, human presses Send, "declared" wording, numbers labeled or derived, [V]/[A]/[D] tags present on provider-dependent and assumed items.
